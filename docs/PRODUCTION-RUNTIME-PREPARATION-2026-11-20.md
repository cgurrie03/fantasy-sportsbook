# Production worker and application preparation — November 20, 2026

This completes the implementation and isolated application testing portion of preparation steps 1 and 2. **No hosted project, scheduler, deployment, account or email was changed.** Live activation and hosted acceptance remain part of the approved cutover.

## Worker implementation

- The Production bundle has an explicit Production project/origin/schema fence. The dedicated function name is `boff-production-live-refresh`; its source dependency manifest is generated by `scripts/prepare-production-worker.mjs` into ignored local artifacts. No credentials are bundled.
- The schema package now includes `supabase/production/worker-runtime.sql`. `supabase/production/configure-worker.sql` installs operator-only cutover helpers. Installing those helpers does not invoke them, configure a secret or start a scheduler.
- Configuration generates a fresh 256-bit credential inside Supabase Vault. Only its hash enters the control cache and private runtime configuration. Cron contains a helper call, never the raw credential. Repeated configuration preserves the same credential and creates only one disabled scheduler. Changed baseline, missing credential or changed cron definition requires review.
- Configuration requires the legacy operation/schedule flags to be off, old jobs to be terminal and the reviewed wallet migration to exist. The existing guarded legacy cron pause script remains unexecuted.
- A prepared release rejects scheduled work before provider access. Explicit warmup may fetch source data and publish the weekly board, but cannot settle tickets, publish/settle futures, award rewards, or deliver notifications. Futures first publish during active runtime, after commissioner rules are reviewed.
- Activation requires platform-owner launch approval, the exact reviewed board/revision and a fresh published board matching the configured season/week. It reconciles `active_week` and enables only the new scheduler. Old automatic weekly balance resets stay retired.
- The reward baseline prevents a new worker from awarding the previous week merely because it was first launched midseason. Notifications remain disabled in Production runtime; email/push activation is a separate task, so historical announcements cannot replay during this cutover.
- `supabase/production/worker-postflight.sql` reports environment, baseline, scheduler state, board freshness/window, legacy jobs and financial-route counts without exposing secrets or scheduler command bodies.

Supabase's documented scheduling pattern uses pg_cron/pg_net with credentials in Vault. The dedicated opaque token is checked by the worker itself; deployment must explicitly use the prepared `verify_jwt:false` setting because this is not a user JWT. Commissioner actions retain their separate database-authorized user JWT path. [Supabase scheduling documentation](https://supabase.com/docs/guides/functions/schedule-functions).

## Integration fix found and corrected

The original Production Week 11 board in the backup had a closing time of November 19 at 8 PM Eastern. The new publisher originally replaced prices/freshness without replacing that old window, producing a published board whose bets were rejected as closed. The Production publisher now validates the incoming source-derived closing window and reconciles the existing board window on both changed and unchanged-price publication paths. Original accepted tickets/lines are untouched. This port is recorded in the generated schema review/hash and covered by the restored-backup placement test.

## What happens at the approved cutover

1. Recheck current source/provider week, pregame benchmarks/featured assignments, existing deployment and job fingerprints. Fence old writers, wait for active leases to finish and take the final encrypted checkpoint.
2. Apply the rehearsed schema package, then perform the owner-reviewed wallet transfer/reservation and job retirement. Install the worker cutover helpers.
3. Deploy the prepared Production function with explicit target/schema settings and platform-managed service credential. Configure it with the reviewed current season/week; its cron remains disabled.
4. Request explicit warmup. Inspect source freshness, complete matchup/player markets, the real board's open/close times, preserved opening benchmarks and featured assignments, and the postflight report. Review current futures rules before opening those markets.
5. Run the hosted member/commissioner/owner acceptance checks using real Supabase Auth and real provider data. Review the exact current board/revision and owner launch approval before activation.
6. Activate the new worker against that reviewed board. Observe subsequent source refreshes and settlement paths. Keep notifications disabled until the separate delivery acceptance task.

The implementation is ready for this controlled integration sequence. It does **not** establish sustained Production IO/capacity or authorize cutover. Full live checks require the upgraded hosted schema and deployment; running them against today's unchanged Production app would test the old implementation.
