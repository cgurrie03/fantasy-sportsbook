## AUD-04 — Invitations and verification

- Commissioner Add/Replace uses invitations for existing and new accounts, including an independently identified Sleeper co-manager.
- Invitation creation validates current Sleeper identity, expected mapping, commissioner access, recipient address, request identity, and issue limits.
- A recipient must sign in with the matching verified email before accepting. Acceptance calls the existing primary/co-manager mapping logic; replacement access is revoked at acceptance, with wallets and history preserved by that logic.
- New/unverified accounts receive a provider-generated verification link. Existing verified accounts receive the direct acceptance link. Verification/signup invitations are the limited exception to the ordinary unverified-recipient communication block.
- Commissioner can resend or cancel pending invitations. Resending replaces the prior pending link; mapping changes invalidate pending links; revoked/expired links cannot grant access.
- Requests are idempotent. Limits are one issuance per Sleeper manager per minute and 32 per issuer/league per day.
- Only token digests are stored in the invitation table. Secret links are not returned to the commissioner API response. Captured email bodies remain owner-only like other Development email captures.
- **Development captures these emails. It does not deliver invitation SMTP mail.** They appear in Platform Owner's existing email log and captured-email preview. This preserves the existing Development mail boundary.
- Wallet approval/funding remains separate. Accepting an invitation does not create a funded wallet.
- Hosted tests used real temporary accounts: existing-account acceptance on mobile, provider email verification for a new account, independent co-manager acceptance, actual Send Invitation/Cancel Invitation UI, and owner email-capture retrieval.
- Rolled-back database tests covered unauthorized issuers, verification, wrong recipient, cancellation, cooldown, resend, repeat acceptance, and independent co-manager mapping. API tests cover 204 responses, retry safety, origin checks, service-only verification generation, and secret-link exclusion.

## AUD-05 — Tuesday 5 AM, no scheduled shutdown

The user's final instruction supersedes the old Tuesday 1 AM–Wednesday 6 AM closure:

> Open when next week's data is ready; advance the week at 5 AM Tuesday; no downtime.

- Weekly selection now uses each NFL week's schedule and its Tuesday **5:00 AM America/New_York** opening boundary, rather than blindly following an early/late provider week change.
- Source readiness is still required. Invalid roster counts, incomplete regular-season matchup pairings, incomplete pricing lineups, or missing game data do not replace the current board.
- Publication remains transactional. The current board is not blanked while a replacement is built. Existing freshness and bet-acceptance guards remain in force; source failures do not authorize stale prices.
- The artificial Tuesday/Wednesday loading flag is removed. Futures, tickets, profile, and credit claims remain accessible.
- Weekly credit-claim eligibility now uses Tuesday 5 AM Eastern as its weekly anchor. The 2-hour/24-hour claims, threshold, futures exclusion, and idempotency rules are retained.
- Fantasy reward processing no longer waits for Wednesday morning.
- Owner schedule and loading copy reflect the new rollover.
- Boundary tests cover immediately before/at 5 AM, early and late provider changes, daylight-saving offsets, and missing upcoming matchup pairings. The first naturally occurring live Tuesday rollover still needs operational observation; the audit did not advance the real clock or publish a fabricated future board.
